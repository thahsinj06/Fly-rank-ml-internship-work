ABSTRACT

Five sentences, one research question

This project asks whether a simple machine learning model can identify content with a higher measured likelihood of decline and help a content team decide what to review first. The analysis uses 30,000 anonymized content records containing search-performance, content, freshness, and engagement signals. A Logistic Regression model using five features was compared with a simple rule-based baseline on the same evaluation data. The model achieved an F1 score of 0.681 on the main random split and 0.648 on a stricter client-grouped validation, with substantially higher recall than the baseline. The resulting output is a ranked decision-support queue using REFRESH, REVIEW, and MONITOR actions for human editorial review.

01 · INTRODUCTION

The decision behind the model

The practical question is simple: which content should a team review first?

1

3

1
Human decision

The model prioritizes; an editor decides.

A wrong prioritization can waste editorial time, while missing genuinely declining content can delay investigation of an important issue. Machine learning can help because several search and content signals can be considered together instead of relying on one simple rule.

Important: The goal is not to automate editorial decisions. The goal is to test whether a simple, interpretable model can provide better decision-support than a transparent baseline.
02 · DATA

What went into the analysis

The analysis uses the anonymized FlyRank ML Internship dataset containing approximately 30,000 content records. The data contains search-performance, content, freshness, and engagement signals.

Target definition

A binary label was created from the supplied trend information: is_declining_label = 1 when trend_direction == "down", otherwise 0.

Model features

Search volume

Demand associated with the content.

90-day impressions

Recent search visibility.

Days since last update

Content freshness signal.

Average position

Search-result position signal.

CTR

Click-through behaviour.

Fields deliberately excluded

  • trend_direction — directly defines the target.
  • trend_pct — related to the supplied trend outcome.
  • content_id — identifier only.
  • client_id — used only for grouped validation, never as a model feature.
Leakage check: target-derived trend fields were excluded from the model. Client identifiers were also excluded from prediction. A remaining limitation is that an exact future-only label window was not available, so temporal overlap cannot be completely ruled out.
03 · METHODOLOGY

Simple model, explicit assumptions

Baseline

The first approach was a transparent rule-based priority score using impressions_90d and days_since_last_update. Higher visibility combined with greater staleness increased review priority. The resulting queue was divided into REFRESH, REVIEW, and MONITOR.

Model

The ML model was Logistic Regression. It was selected because it is fast, relatively easy to interpret, and appropriate for testing whether multiple signals provide useful classification beyond the baseline.

Preprocessing

Missing numerical values were handled using median imputation and the features were standardized before Logistic Regression.

Validation design

The main evaluation used an 80/20 stratified random split with random_state=42. A second client-grouped validation kept records from the same client together to test stricter generalization across client groups.

Research framing: The model predicts the supplied decline label. It does not predict Google's algorithm, and it does not establish that a content refresh will cause search performance to improve.

What the numbers mean

The model improves F1 from 0.529 to 0.681 on the main split and increases recall from 0.475 to 0.873. The trade-off is lower precision: the model flags more content, including some items that are not in the declining class.

For a screening workflow, this trade-off can be useful because the purpose is to create a review queue rather than make automatic publishing or content-removal decisions.

Generalization check

The client-grouped validation produced an F1 of 0.648, compared with 0.681 on the random split. The decrease indicates that performance is weaker when the model must generalize across client groups.

05 · LIMITATIONS

What this analysis cannot claim

Not a future-only test

The available data did not provide an exact future-only label window, so this is not a fully time-separated forecasting experiment.

Proxy target

The target is based on the supplied trend direction rather than a direct future business outcome.

Limited validation

The analysis uses a main random split and one client-grouped validation. More time-held-out and client-held-out tests would strengthen the result.

No causal claim

The analysis does not show that refreshing a page causes its performance to improve.

Dataset scope

An anonymized internship dataset may not represent every industry, website, or search environment.

Decision-support only

Scores should support human review, not automatically publish, delete, redirect, or rewrite content.

Honest framing: The results are measured and directional. They demonstrate a useful decision-support experiment, not a production guarantee or causal SEO strategy.
06 · RANKED RECOMMENDATIONS

From prediction to action

The model becomes useful when its scores help an editor decide where to spend attention first.

01

REFRESH

Start with the highest-priority content. Check whether the page is outdated, no longer matches search intent, or has lost useful information.

02

REVIEW

Investigate medium-priority content using additional evidence such as recent search performance, content quality, and business importance.

03

MONITOR

Keep lower-priority content under normal observation instead of spending immediate editorial resources on it.

The proposed workflow

Rank → inspect evidence → human decision → action.

Confidence in these recommendations is moderate. The model's strong recall and improved F1 support its use as a screening layer, but the lower client-grouped performance and lack of a fully time-separated evaluation limit generalization.

07 · REPRODUCIBILITY

Everything starts from the notebook

The complete implementation is contained in the capstone notebook: work/notebooks/capstone.ipynb

Reproduction flow

  1. Load the anonymized dataset.
  2. Define the decline label.
  3. Remove target-derived and identifier fields.
  4. Select the five model features.
  5. Build the rule-based baseline.
  6. Create the stratified 80/20 split.
  7. Train Logistic Regression.
  8. Evaluate model and baseline using the same metrics.
  9. Run client-grouped validation.
  10. Generate the ranked action queue and supporting outputs.

The main evaluation uses random_state=42 for reproducibility. The reported values are generated from the capstone notebook rather than being manually estimated.
